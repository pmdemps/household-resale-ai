**Pattern across all of them:** the three things users praise are (1) *one place to see everything*, (2) *never double-sell* (auto-delist), (3) *it took seconds*. The three things they hate are (1) silent sync failures / missed sales, (2) re-login friction, (3) confusing pricing/tiers. Nobody is praised for analytics depth.

### Borrowable UX recommendations for a non-technical co-user

1. **Home = three numbers + one list.** Top: "Needs you" count, "Live" count, "This month's profit" (signed, colored). Below: the Needs-you list only. Vendoo's win is "everything in one place"; Flyp's loss is a bare order list.
2. **Plain-English item states, max five:** *Not listed yet · Live · Offer waiting · Sold – ship it · Done*. Hide `draft/pending/published/withdrawn` API states behind these. Poshmark's "Not For Sale"/"Available" shows plain words work.
3. **Offers are a card, not a table.** "Someone offered **$12** for *Kids' Nike sneakers* on Vinted. You'd keep **$12.00**. Floor is $10." Two buttons: *Accept* / *Counter* (+ small *Decline*). Show the countdown (Poshmark/eBay offers expire; 24 h on Poshmark).
4. **Always show "you'd keep", never the gross.** Fees differ wildly (Vinted 0% vs Poshmark 20%); the repo's `lib/fees.ts` already exists for this.
5. **"Sold somewhere → take it down everywhere" must be loud and automatic.** This is the single most-praised feature (Vendoo) and the most-hated failure (OneShop, Vendoo missed-sale → double sale). Show a red banner until every `delist` task is done.
6. **Photo-first add flow:** camera → AI suggests title/condition/category → human edits → price with "you'd keep" preview → pick platforms with checkboxes. eBay's own app and Nifty do photo→draft; users accept AI output that needs "only a few manual edits".
7. **One form, not one per marketplace.** Crosslist's single form is praised; Vendoo's per-marketplace forms are the main workflow complaint. Keep platform-specific fields in a collapsed "eBay details" section.
8. **Hide from the home screen:** SKUs, offer IDs, API status, activity log, token expiry, agent tasks that are not `pending`. Put them under Settings → "Advanced".
9. **Connection health in plain words:** "eBay connected ✓ · last checked 5 min ago" / "eBay needs you to sign in again" (re-login friction is a top complaint).
10. **Money page:** monthly bar chart of *net profit* (sale − fees − shipping − cost basis), bars above/below zero in two colors; under it: "Sold this month", "Fees paid", "Still listed (value at asking price)", and a per-platform split. Keep "cost basis" optional so profit never shows as blank.
11. **Approve-with-one-tap, from a notification.** The roadmap's push text ("…offer $3.99 · you'd get $3.99. Accept?") is exactly right; make the notification deep-link to the offer card.
12. **No tiers, no add-ons, no jargon in copy.** Use "listing" not "offer" for eBay's `offer` object (eBay's naming collides with buyer offers — pick *listing* in UI and *offer* only for buyer offers).

## 2. eBay Sell integration (precise)

### Developer account, keyset, RuName, account-deletion endpoint
- Join the Developer Program → one **keyset per environment** (Sandbox + Production), each with App ID (client_id), Cert ID (client_secret), and an **RuName** that maps to your Accept URL; `redirect_uri` in OAuth *is the RuName*, not your URL ([consent docs](https://developer.ebay.com/api-docs/static/oauth-consent-request.html)).
- **Production keyset is activated only after** you either subscribe to Marketplace Account Deletion notifications or opt out via the **"Not persisting eBay data"** toggle; non-compliance → loss of API access ([MAD page](https://developer.ebay.com/marketplace-account-deletion)). Because Resale HQ stores eBay user tokens/order data, do **not** take the exemption.
- **Challenge verification** (GET `your-endpoint?challenge_code=...`): `challengeResponse = hex(SHA256(challengeCode + verificationToken + endpointURL))` — *in that order*; reply `200`, `Content-Type: application/json`, body `{"challengeResponse":"<hex>"}`; build JSON with a library (a hand-written string can prepend a BOM). Verification token: 32–80 chars, `[A-Za-z0-9_-]` only. Endpoint must be HTTPS, no localhost/internal IP ([MAD page](https://developer.ebay.com/marketplace-account-deletion)).
- **Notification POST** shape: `metadata.topic = "MARKETPLACE_ACCOUNT_DELETION"`, `metadata.schemaVersion`, `notification.notificationId`, `eventDate`, `publishDate`, `publishAttemptCount`, `notification.data.{username,userId,eiasToken}`. Ack with 200/201/202/204 immediately; unacked 24 h → endpoint marked down + alert email, 30 days to fix ([MAD page](https://developer.ebay.com/marketplace-account-deletion)). Verify `X-EBAY-SIGNATURE` via Notification API `getPublicKey` ([comms guide](https://developer.ebay.com/develop/guides/sell-communications-guide.md)). Handler: delete that user's tokens/rows, log it.

### OAuth 2.0 authorization-code grant (user tokens)
- Authorize: `https://auth.sandbox.ebay.com/oauth2/authorize` / `https://auth.ebay.com/oauth2/authorize` with `client_id, redirect_uri=<RuName>, response_type=code, scope=<space-separated, URL-encoded>, state, prompt=login` ([consent docs](https://developer.ebay.com/api-docs/static/oauth-consent-request.html); hosts **[UNVERIFIED]** from page text but confirmed as `authorizationUrl` in the Inventory OpenAPI spec for production).
- Token: `POST https://api.sandbox.ebay.com/identity/v1/oauth2/token` / `https://api.ebay.com/identity/v1/oauth2/token`, headers `Content-Type: application/x-www-form-urlencoded`, `Authorization: Basic base64(client_id:client_secret)`, body `grant_type=authorization_code&code=...&redirect_uri=<RuName>` (decode the code before your client re-encodes it). Response: `access_token`, `expires_in: 7200`, `refresh_token`, `refresh_token_expires_in: 47304000` (~547 days ≈ 18 months), `token_type` ([exchange docs](https://developer.ebay.com/api-docs/static/oauth-auth-code-grant-request.html)).
- Refresh: same endpoint/headers, `grant_type=refresh_token&refresh_token=...&scope=<same or subset>`; response has a new `access_token` but **no new refresh_token** (user must re-consent after ~18 months). Refresh grant limit 50,000/day ([refresh docs](https://developer.ebay.com/api-docs/static/oauth-refresh-token-request.html)).
- **Scopes to request** (all prefixed `https://api.ebay.com/oauth/api_scope/`): `sell.inventory` (Inventory API; also the Negotiation API per its spec ([SDK](https://github.com/michabbb/sdk-ebay-rest-negotiation))), `sell.account` (business policies) **[UNVERIFIED scope name; standard]**, `sell.fulfillment` (orders; listed as the ORDER_CONFIRMATION topic scope ([topics](https://developer.ebay.com/develop/api/sell/notification_events))), `commerce.notification.subscription` (user-level notification subscriptions ([comms guide](https://developer.ebay.com/develop/guides/sell-communications-guide.md))). Trading API calls accept an OAuth token in `X-EBAY-API-IAF-TOKEN` and need the scope listed on each call's page ([Trading+OAuth](https://developer.ebay.com/api-docs/static/oauth-trad-apis.html)); for Best Offer calls that is `sell.inventory` **[UNVERIFIED — confirm on the RespondToBestOffer page before tonight]**. Taxonomy API only needs the base `api_scope` with **client-credentials** ([taxonomy spec](https://developer.ebay.com/api-docs/master/commerce/taxonomy/openapi/3/commerce_taxonomy_v1_oas3.json)).

### Listing creation (Inventory API, base `https://api.ebay.com/sell/inventory/v1`, sandbox `api.sandbox.ebay.com`)
Order of calls: location → inventory item → offer → publish.
1. `POST /location/{merchantLocationKey}` once: `location.address.{city,stateOrProvince,postalCode,country:"US"}` (warehouse needs only city/state/country), `locationTypes:["WAREHOUSE"]`, `merchantLocationStatus:"ENABLED"` (defaults). Key ≤36 chars; address is immutable after creation (spec).
2. `PUT /inventory_item/{sku}` — **`Content-Language: en-US` header is required** (marked required in spec; `en_US` with underscore fails — a classic gotcha ([community](https://community.ebay.com/t5/eBay-APIs-Talk-to-your-fellow/Help-Needed-eBay-Inventory-API-quot-Invalid-value-for-header/m-p/35139601))). SKU ≤50 chars. Body: `availability.shipToLocationAvailability.quantity: 1`, `condition` (ConditionEnum; used goods: `USED_EXCELLENT`, `USED_VERY_GOOD`, `USED_GOOD`, `USED_ACCEPTABLE`; new: `NEW`, `LIKE_NEW`, `NEW_OTHER`, `NEW_WITH_DEFECTS` — the "new" set is named in the spec's `conditionDescription` text; the used list is **[UNVERIFIED enum spelling, standard]**; check category support via Metadata `getItemConditionPolicies`), `conditionDescription` (≤1000 chars, used items only), `product.title` (**≤80 chars**), `product.description` (HTML ok, no active content), `product.imageUrls` (**HTTPS only, ≥1 required to publish, ≤24**; EPS alternative via Trading `UploadSiteHostedPictures`), `product.aspects: {"Brand":["Nike"],"Size":["10"]}`, optional `packageWeightAndSize` (needed for calculated shipping). 204 on success. Source: spec text parsed locally.
3. `POST /offer` — also **requires `Content-Language`**. Body: `sku`, `marketplaceId:"EBAY_US"`, `format:"FIXED_PRICE"`, `listingDuration:"GTC"` (mandatory for fixed price), `availableQuantity:1`, `categoryId`, `listingDescription` (falls back to product.description), `merchantLocationKey`, `pricingSummary.price:{value:"19.99",currency:"USD"}`, `listingPolicies:{fulfillmentPolicyId,paymentPolicyId,returnPolicyId, bestOfferTerms:{bestOfferEnabled:true, autoDeclinePrice:{value,currency}, autoAcceptPrice:{value,currency}}}`. Only `sku`, `marketplaceId`, `format` are needed to *create*; the rest is needed to *publish*. One offer per SKU per marketplace. Returns `offerId` (201).
4. `POST /offer/{offerId}/publish/` → `{listingId}`. Price/qty changes: `PUT /offer/{offerId}` (`Content-Language` again) or `POST /bulk_update_price_quantity`; end listing: `POST /offer/{offerId}/withdraw` (offer stays as unpublished, re-publishable). `POST /offer/get_listing_fees` previews fees.
- **Business policies:** seller must be opted in; fetch IDs via Account API `GET /sell/account/v1/fulfillment_policy?marketplace_id=EBAY_US`, `/payment_policy`, `/return_policy` **[UNVERIFIED paths, standard]**. Sandbox users often cannot opt in (catch-22 threads: [1](https://community.ebay.com/t5/RESTful-Sell-APIs-Account/Cannot-Opt-In-New-Sandbox-User-to-Business-Policies-Catch-22/td-p/35376198), [2](https://community.ebay.com/t5/Token-Messaging-Sandbox-related/sandbox-test-user-does-not-have-permission-to-create-business/m-p/35175074)) — try Account API `optInToProgram` `SELLING_POLICY_MANAGEMENT`, else create policies via `POST /sell/account/v1/fulfillment_policy` after opt-in.
- **Taxonomy** (`https://api.ebay.com/commerce/taxonomy/v1`): `GET /get_default_category_tree_id?marketplace_id=EBAY_US` → `categoryTreeId` ("0" for US), `GET /category_tree/0/get_category_suggestions?q=kids nike sneakers` → `categorySuggestions[].category.{categoryId,categoryName}` (**not supported in Sandbox** — returns boilerplate), `GET /category_tree/0/get_item_aspects_for_category?category_id=<leaf>` → `aspects[].localizedAspectName, aspectConstraint.aspectRequired, aspectValues[].localizedValue` ([taxonomy spec](https://developer.ebay.com/api-docs/master/commerce/taxonomy/openapi/3/commerce_taxonomy_v1_oas3.json)).
- The Account API `getFulfillmentPolicies` and Metadata API detail pages were not fetched; everything marked standard is from eBay's long-stable REST shape.

### Buyer Best Offers (Trading API, XML)
- Endpoint `POST https://api.ebay.com/ws/api.dll` (sandbox `https://api.sandbox.ebay.com/ws/api.dll`). Headers: `X-EBAY-API-CALL-NAME: GetBestOffers`, `X-EBAY-API-SITEID: 0`, `X-EBAY-API-COMPATIBILITY-LEVEL: 1423` (any current level), `X-EBAY-API-IAF-TOKEN: <OAuth user access token>`, `Content-Type: text/xml`; omit `RequesterCredentials` when using IAF ([Making a call](https://developer.ebay.com/DevZone/XML/Docs/Concepts/MakingACall.html)).
- `GetBestOffers`: with no `ItemID`/`BestOfferID` it returns IDs of all *active* offers for the seller (up to 10,000); with `ItemID` returns that listing's offers; `BestOfferStatus` defaults `Active` (`All` only with ItemID); `DetailLevel: ReturnAll` needed for `BuyerMessage`. Response `BestOfferArray.BestOffer{BestOfferID, BestOfferCodeType (BuyerBestOffer|BuyerCounterOffer|SellerCounterOffer), Buyer.UserID, Price@currencyID, Quantity, Status, ExpirationTime, BuyerMessage}`, `Item{ItemID, ListingDetails.EndTime}` ([GetBestOffers](https://developer.ebay.com/DevZone/XML/Docs/Reference/eBay/GetBestOffers.html)).
- `RespondToBestOffer`: `<RespondToBestOfferRequest xmlns="urn:ebay:apis:eBLBaseComponents"><ItemID/><BestOfferID/><Action>Accept|Counter|Decline</Action><CounterOfferPrice currencyID="USD">12.00</CounterOfferPrice><CounterOfferQuantity>1</CounterOfferQuantity><SellerResponse>≤250 chars</SellerResponse></RespondToBestOfferRequest>`. Can decline many offers in one call, but **accept/counter only one per call**; counter price ≤ Buy It Now price. Response `BestOffer.CallStatus`, `Ack` ([RespondToBestOffer](https://developer.ebay.com/DevZone/XML/Docs/Reference/eBay/RespondToBestOffer.html)).
- Newer REST/GraphQL offer management: no public REST method to *respond* to a buyer's Best Offer was found; the Negotiation API (`/sell/negotiation/v1/find_eligible_items`, `/send_offer_to_interested_buyers`) is seller→buyer only ([SDK](https://github.com/michabbb/sdk-ebay-rest-negotiation)). Trading API remains the path. **[UNVERIFIED: no GraphQL option publicly documented.]**
- **Getting notified:** Commerce Notification API has topic **`OFFER_ACTIVITY`** (events `BUYER_OFFER`, `BUYER_COUNTER_OFFER`, `SELLER_OFFER`, `SELLER_COUNTER_OFFER`; HTTPS POST, 3 retries) ([topics](https://developer.ebay.com/develop/api/sell/notification_events)). Setup: `createDestination` (same challenge recipe as account-deletion) → `createSubscription{topicId, destinationId, status}`; user-level subscriptions need `commerce.notification.subscription` scope; `testSubscription` exists ([comms guide](https://developer.ebay.com/develop/guides/sell-communications-guide.md)). Legacy Platform Notifications `BestOfferPlaced`/`BestOfferDeclined`/`CounterOfferReceived` are **buyer-facing** per the guide — not what we want. Realistic plan: subscribe to `OFFER_ACTIVITY` *and* poll `GetBestOffers` every 10–15 min as a safety net (Trading API is 5,000 calls/day; polling every 10 min = 144/day).
- **Rate limits (defaults):** Inventory 2M/day, Account 25k/day, Fulfillment orders 100k/day, Taxonomy 5k/day, Negotiation 1M/day, Notification 10k/day, **Trading 5k/day**, Identity 5k/day; raise via Application Growth Check ([limits](https://developer.ebay.com/develop/get-started/api-call-limits)).
- **Sandbox tips:** create users at Developer Portal → Tools & Samples → "Sandbox user registration"; names get `TESTUSER_` prefix; make a seller *and* a buyer so the buyer can place a Best Offer; accounts get $500k play money refreshed weekly ([sandbox users](https://developer.ebay.com/api-docs/static/sandbox-test-users.html)). Sandbox tokens only work in sandbox ([exchange docs](https://developer.ebay.com/api-docs/static/oauth-auth-code-grant-request.html)). Category suggestions don't work in sandbox — hardcode a leaf category (e.g. use production Taxonomy with client-credentials to look it up).

## 3. Etsy Open API v3

- **Registration/approval:** register an app, declare *personal* (own shop / testing) vs *commercial* (multiple shops) use; Etsy must approve the app's purpose before API access; a monitored support email is required; 6 months of no calls → suspension ([API Terms](https://www.etsy.com/legal/api)). Etsy is currently "revisiting" the App Key process; user reports: personal access took ~3 weeks, commercial approvals stuck for months, some personal keys cancelled on requesting commercial ([GitHub #1607](https://github.com/etsy/open-api/discussions/1607)). **Apply as personal, own-shop only.**
- **Rate limits:** per-key QPS + QPD (rolling 24 h window), values shown in Developer Portal; 429 + `retry-after`; headers `x-limit-per-second`, `x-remaining-this-second`, `x-limit-per-day`, `x-remaining-today` ([rate limits](https://developer.etsy.com/documentation/essentials/rate-limits)). The commonly cited 10 QPS / 10,000 QPD default is **[UNVERIFIED]** (page gives no fixed numbers).
- **Headers:** every call `x-api-key: <keystring>` (the requests page says keystring:shared_secret, the auth page says keystring — send the keystring **[UNVERIFIED which]**) + `Authorization: Bearer <user_id>.<token>`; base `https://api.etsy.com/v3/application/` (= `openapi.etsy.com`) ([requests](https://developer.etsy.com/documentation/essentials/requests)).
- **OAuth PKCE:** `GET https://www.etsy.com/oauth/connect?response_type=code&redirect_uri=<exact registered HTTPS URL>&scope=<space-separated>&client_id=<keystring>&state=<nonce>&code_challenge=<S256>&code_challenge_method=S256`; token `POST https://api.etsy.com/v3/public/oauth/token` (`grant_type=authorization_code, client_id, redirect_uri, code, code_verifier`) → `access_token` (prefixed `user_id.`), `expires_in: 3600`, `refresh_token`, `scope`; refresh with `grant_type=refresh_token, client_id, refresh_token`; **refresh token lives 90 days** and keeps original scope ([auth](https://developer.etsy.com/documentation/essentials/authentication)). Scopes: `listings_r listings_w listings_d shops_r shops_w transactions_r transactions_w email_r profile_r address_r`. Request `listings_r listings_w shops_r transactions_r` (+ `email_r` only if you want the account email). `user_id` = the prefix of `access_token`; shop via `GET /v3/application/users/me` → `{user_id, shop_id}` and `GET /v3/application/users/{user_id}/shops` **[UNVERIFIED — reference page unfetchable; standard]**.
- **Create listing:** `POST /v3/application/shops/{shop_id}/listings` (scope `listings_w`) minimum `quantity, title, description, price, who_made, when_made, taxonomy_id`; physical items also need `shipping_profile_id` and `readiness_state_id`; `image_ids` needed before activation ([listings tutorial](https://developer.etsy.com/documentation/tutorials/listings)). `return_policy_id` is required for physical listings in current API **[UNVERIFIED]**; title ≤140 chars, ≤13 tags **[UNVERIFIED]**. `who_made ∈ {i_did, someone_else, collective}` **[UNVERIFIED from page; standard]**; `when_made` enum per Etsy's June-2025 notice: `made_to_order, 2020_2025, 2010_2019, 2006_2009, before_2006, 2000_2005, 1990s … 1700s, before_1700`; a May-2026 comment claims it rolled to `2020_2026, 2007_2009, before_2007, 2000_2006` — invalid values return 400, so **fetch-and-test before hardcoding** ([GitHub #1414](https://github.com/etsy/open-api/discussions/1414)). Vintage = `who_made: someone_else` + a `when_made` decade ≥20 years old.
- Images: `POST /v3/application/shops/{shop_id}/listings/{listing_id}/images` multipart, file field `image` (or `listing_image_id` to reuse), optional `rank` ([tutorial](https://developer.etsy.com/documentation/tutorials/listings)). Activate: `PATCH /v3/application/shops/{shop_id}/listings/{listing_id}` with `state=active` (needs ≥1 image). Shipping profiles: `GET /v3/application/shops/{shop_id}/shipping-profiles` (`shops_r`); taxonomy: `GET /v3/application/seller-taxonomy/nodes`. Listing fee $0.20 is charged on activation (drafts free) **[UNVERIFIED from API docs; matches Etsy fee policy and roadmap]**.
- **Policy:** API Terms forbid facilitating listings that violate the Creativity Standards (mass-produced/non-handmade); also no AI-training on Etsy data, 6 h max staleness for listing data, required attribution line "The term 'Etsy' is a trademark of Etsy, Inc. This Application uses Etsy's API, but is not endorsed or certified by Etsy." ([API Terms](https://www.etsy.com/legal/api)).
- **Reading sales:** `GET /v3/application/shops/{shop_id}/receipts?was_paid=true&min_created=<unix>&limit=…` (scope `transactions_r`) **[UNVERIFIED params; standard]**. **Etsy v3 has no webhooks** — not mentioned anywhere in the auth/requests/rate-limit docs and third-party integrators poll ([TinyCommand](https://site.tinycommand.com/integrations/etsy)); confirm by absence **[UNVERIFIED]**. Poll hourly.

## 4. Vinted / Poshmark / Mercari notification emails (Gmail watcher)

Official statements found: Vinted US says real mail comes from an address **ending `@vinted.com`** ([Vinted help](https://www.vinted.com/help/628-recognize-spoof-and-phishing-messages)); UK sellers see **`@vinted.co.uk`** ([InboxGuard](https://inboxguard.app/blog/is-this-email-from-vinted-real)) — so match on domain suffix `vinted.(com|co.uk|fr|de…)` **and** DKIM/SPF pass, not an exact address. Poshmark: "Real emails come from `@poshmark.com`" (third-party, [Closo](https://closo.co/blogs/blog/the-real-truth-about-poshmark-scams-kindly-email-me-and-other-red-flags-2025-guide)) **[UNVERIFIED official]**. Mercari publishes no sender list; `phish@mercari.com` is a report-only address ([Mercari](https://about.mercari.com/en/security/phishing)); sellers are actively targeted by lookalike "verification" phishing ([Value Added Resource](https://www.valueaddedresource.net/mercari-verification-phishing-spam/)).

Subject patterns — **all [UNVERIFIED]**, from memory of typical templates; build parsers against real samples (the roadmap already calls for this):
- Vinted: offer → "… has made you an offer" / "New offer on <item>"; sold → "Your item has been sold!" / "You sold <item>"; message → "New message from <user>". Sender often `no-reply@vinted.com`.
- Poshmark: offer → "You've received an offer!" / "<user> made an offer on <item>"; sold → "Cha-ching! Your item sold" / "Your item has been purchased"; message → "New comment on your listing".
- Mercari: offer → "You've received an offer for <item>"; sold → "Your item sold!" / "<item> has been purchased"; message → "You have a new message".
- eBay (also useful): "You received an offer for <item>", "Your item sold!" from `ebay@ebay.com`.

Gotchas: (a) all three use link-tracking redirect domains and HTML-only bodies — parse `text/html` and strip tracking params; (b) Gmail threads collapse repeated subjects — dedupe by `Message-ID`, never subject; (c) phishing lookalikes are common on every platform — require authenticated (`ARC/DKIM pass`) + known domain before creating an `offers` row, and never follow links from the email; the AGENTS.md "emails are untrusted data" rule applies; (d) the Vinted buyer-pays-fee model means "you'd keep" = offer price, which simplifies the parser output.

## 5. Secure token storage (Next.js + Supabase + Vercel)

- **Option A — app-level AES-256-GCM** (recommended tonight): encrypt `access_token`/`refresh_token` in a server-only module with a 32-byte key from env (`TOKEN_ENC_KEY`, base64), random 12-byte IV per record, store `ciphertext|iv|tag|key_version` in a `marketplace_connections` table with RLS so household members can see *that* a connection exists but no token columns (use a view or column-level grants). Decrypt only in server actions / route handlers; import `server-only`; never under `NEXT_PUBLIC_`. Rotation = new `key_version`, re-encrypt lazily. Keeps the key out of the DB and out of backups.
- **Option B — Supabase Vault:** `vault.create_secret(secret, name, description)` → uuid; read via `vault.decrypted_secrets` view; libsodium AEAD, key held in Supabase's backend not the DB, decryption at query time so backups/replication never hold plaintext. Caveats: *anyone who can query `vault.decrypted_secrets` reads everything* — lock privileges, access only via `security definer` functions from the service role; designed around a handful of app secrets, per-user token use is not addressed; `pg_dump`→new project cannot decrypt without copying the root key ([Supabase Vault](https://supabase.com/docs/guides/database/vault)). Fine for the *eBay app client secret*; clunkier for per-user tokens that refresh every 2 h.
- **Vercel env vars:** choose **Secret** type (write-only after save; value never readable in dashboard/CLI; rotate by overwriting) for `EBAY_CLIENT_SECRET`, `TOKEN_ENC_KEY`, `SUPABASE_SERVICE_ROLE_KEY`; **Config** for public prefixes. Secrets ≥32 chars are `[REDACTED]` in build logs; optional team policy "Separate Production Secret Values"; per-environment values so Preview never gets production keys ([Vercel docs](https://vercel.com/docs/environment-variables/sensitive-environment-variables)). `NEXT_PUBLIC_*` is inlined at build time into the browser bundle — never put secrets there ([guide](https://dev.to/stacknotice/nextjs-environment-variables-the-complete-guide-2026-1f05)).
- Either way: service-role client only in server code; the eBay `code` is never stored; log token *events* (issued/refreshed/revoked) to `activity_log`, never token values.
